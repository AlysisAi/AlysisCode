# Original host approval expiry

The engine now requires the host's existing `approval_preflight.expires_at` for prepared Computer Use actions. It accepts only canonical UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, a real calendar date, and a deadline no more than 30 seconds in the future. Missing, malformed or already expired challenges never reach execution. The token is retained only inside the existing authenticated preflight/execute exchange; it is not added to model output, ordinary event buffers or approval metadata.

A private absolute-expiry and monotonic-deadline pair is passed to `_request_approval`. The pending approval's displayed `expires_at` is the earlier of the original host expiry and any shorter engine approval cap. The monotonic deadline is captured before binding construction or UI emission. Time spent transporting preflight, building the approval, or reviewing in the app is deducted; the wait starts with only the remaining time. Non-host generic and persistent swarm approvals keep their prior behavior.

Bound approval responses are rejected at the deadline, including exact equality. UTC expiry and monotonic time independently bound host approvals. The engine rechecks both immediately before execute, including after an exact cached turn permission. This also prevents a wall-clock rollback from extending the original wait. A forward jump or expiry during event delivery cannot revive the token. Explicit cancellation remains dominant, no automatic retry occurs, and no new nonce, grant, lease or approval is generated by expiry handling. A failed expiry returns `computer_use_approval_expired` stating that the action was not dispatched; it does not claim that earlier actions had no effect.

Controlled-clock tests cover delayed preflight, review duration, a shorter engine cap, real fingerprint-bound Allow before/at/after expiry, clock changes, expiry after Allow and cached turn permission, cancellation, malformed deadlines and expiry during approval preparation. The existing real protocol tests retain exact action/route/job/tool fingerprints and token privacy checks. No 30-second elapsed wait or live provider/browser is used.

App wording, review-button expiry, and its native confirmation dialog are handled separately. This engine change supplies the same original deadline through the existing `expires_at` field; it neither removes confirmation nor promises resumed execution after expiry.
